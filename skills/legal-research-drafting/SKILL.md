# 法律研究与文书审校

将法律任务按“事实结构化 → 争点与请求权 → 元典检索 → 规则提炼 → 事实涵摄 → 计算 → 起草 → 审校”顺序完成。不得跳过检索直接凭记忆写具体条号、案号或裁判规则。

## 1. 确定任务边界

先识别以下内容：

- 法域、当事人立场、目标产物和使用场景；
- 法律事实发生地、行为发生日、合同签订日、通知到达日、立案或受理日、裁判及执行阶段；
- 已有证据、缺失证据和对方可能提出的抗辩；
- 用户要的是法律判断、行动方案、金额计算，还是可提交文书。
- 用户指定的字数、案例数量、格式、视角和交付形态；这些属于硬约束，优先于默认完整性要求。

**体例与模板查表（凡产出可交付文书必做）**：识别出目标文书类型后，先完整读取 [法律文书体例与版式决策指南](references/legal-document-style-guide.md)，确定该文种应采用诉讼文书体、说理体、函件体、决议体、章条体或报告体，并完成当事人信息、标题层级和表格必要性判断；再读取 [模板查询表](references/templates-index.md)，定位该类型的模板参考文件，通读其体例骨架、必备要素清单与填写要点，作为第 8 步起草的体例依据。表中没有的类型选最接近类目参照。模板与题目显性指令冲突时，题目指令优先。

缺少会改变请求权、管辖、期间、责任主体或计算结果的事实时，优先继续完成不受影响的检索和分析；用条件分支呈现结果，并集中列出待确认事项。不要擅自补齐事实。

在此步同时抽取**显性指令清单**：逐条列出题目或用户指令中的全部显性要求——要求起草的每份文书、要求处理或分析的每个争点、附带的分析／说明任务（即使与文书本体相对独立）、负向指令（“不得……”“不把……列入”）、数量与格式约束。该清单在第 9 步审校时逐项销项；任何一项未覆盖即视为任务未完成。文书本体之外的附带分析任务不得因为“文书已写完”而省略。**封闭式规则禁开口（硬约束）**：题目给定封闭式例外清单、硬性流程规则或固定分档参数的（如“例外仅限……”“必须先……后……”），文书不得增设任何新例外、缓冲机制、变通通道或替代流程——补充例外属于改变题目给定的制度设计，即使出于商业合理性也不允许；确有必要提示的，写入对话回复的建议部分而非文书本体。**文书篇幅简单不等于任务简单**：委托书、函件、通知类短文书的题目若要求判断资格、条件、效力或说明理由，该判断同样须完成法条检索与论证（结论落在文书本体或附随说明中），不得因文书本体短小而省略检索。

## 2. 建立分析框架

先定性，后定量。按法律关系拆分争议焦点，不把实体责任、程序救济、费用负担和损害赔偿混为一体。

- 民商事：请求权基础、构成要件、抗辩、举证责任、法律后果。
- 刑事：客体、客观方面、主体、主观方面，再分析数额、情节和刑罚。
- 行政：职权依据、事实认定、程序、法律适用、裁量和救济。
- 劳动：劳动关系、解除或终止事由、通知与到达、工资基数、工作年限、仲裁时效和请求项目。
- 破产与执行：程序状态、责任主体、权利顺位、申报或异议路径、费用规则和另行赔偿请求权。

内部先形成“争点—待证事实—可能规则—所需证据”清单，再检索。

## 3. 强制执行元典检索

### 3.1 法规检索

使用 `legal-statute-retrieval`：

1. 用 `semantic` 或 `search_article` 发现可能相关的法条与司法解释。
2. 用 `search_regulation` 定位法规全称、发布机关、效力和版本。
3. 对主线法规用 `regulation_detail` 查看适用范围、附则、衔接和修改情况。
4. 对最终引用的每一条规则用 `article_detail` 读取原文；已知法规 ID 时优先用法条 ID。
5. 涉及历史法律事实时，向 `article_detail` 或 `regulation_detail` 传入 `refer_date`，同时查询当前版本，明确新旧规则差异和时间效力依据。

发现型检索每次设置 `top_k` 为 3 至 5；单一争点原则上不超过两轮不同关键词检索。命中法规全称和目标条文后转入详情查询，不继续扩大语义结果集。

不得把搜索摘要当成最终法条原文。查询为空、超时、鉴权失败或返回错误时，换法规全称、条号、关键词或 ID 重试；仍无法核实时标记“待专业人士核实”，不得编造。

### 3.2 案例检索

下列情形必须使用 `legal-case-retrieval`：规则存在争议、法条含开放性概念、金额或责任比例依赖裁判口径、需要证明地方实践、用户要求类案或预计对方会提出相反观点。

1. 先用 `semantic` 且 `only_authoritative=true`，或 `keyword` 且 `authoritative=true` 检索指导性、参考、公报、典型等权威案例。
2. 再按需要检索普通案例，并优先选择受诉法院所在地、较高层级、较新且争点匹配的裁判。
3. 先根据搜索结果筛选严格匹配的候选案例，再对最相关的 1 至 2 件使用 `detail`；不要并行读取多篇可能无关的长判决。引用判项、裁判理由或原文前必须读取全文；只有摘要时不得写成法院原话。
4. 对每个案例说明关键事实、裁判规则、与本案的相同点及差异点。普通案例只作参考，不写成普遍强制规则。
5. 同一案件不同审级不重复计数；严格命中和近似类比分开标注。
6. **地位标签以检索返回为准**：案例地位（指导性案例、公报案例、人民法院案例库参考案例、典型案例等）只能采用检索工具返回的类型字段原文；发布主体（最高法／高院／中院／基层法院等）以检索返回的来源信息为准，不得升格。权威库查无记录的一律按普通判例引用并注明无强制约束力。
7. **观点方向确认**：援引案例中的认定或规则前，确认其为该案生效裁判（或抗诉、再审改判后）的立场；被上级法院纠正、撤销或否定的原审认定不得作为支持性依据引用。
8. **未核验不引用（硬约束）**：写入文书的每一个具体案号，其真实性、地位标签、观点立场三项必须全部经检索核验通过。检索工具不可用（额度耗尽、持续报错）或检索未命中时，不得凭记忆写出任何具体案号——改为仅以法条和规则论证，必要时注明"类案检索暂不可用，建议补充检索"。少引或不引案例是合规结果，引用未核验案例是违规结果。

案例检索每次设置 `top_k` 为 3 至 5。用户指定案例数量时严格遵守；用户未指定时只读取一件严格匹配案例，确有冲突时才增加第二件。一条明确法条加一件严格匹配案例已足以支持结论时，立即进入事实适用和输出；除非规则存在真实分歧或用户要求全面研究，不继续扩张检索范围。检索质量优先于数量，避免把长篇、弱相关工具结果全部带入上下文。

### 3.3 长尾法源与动态信息核验

以下四类引用是编造和过时风险的高发区，必须按对应规则处理，元典核验不能替代：

1. **元典未收录的规范性文件**（地方法院文件、部委规范性文件、行业规则等）：必须用 `legal-web-search` 检索并用 `web-page-fetch` 读取一手发布页核验名称、文号、发布机关后才能引用；核验不到的一律不引用，也不得以“据了解”“实践中有规定”等方式暗示其存在。
2. **规范性文件时效**：部门和地方规范性文件常设有效期或被后续文件废止。引用前须确认其是否仍然有效；已失效、已废止或有效期届满的必须标注时效状态，不得表述为现行依据。
3. **“最新／截至目前／尚无”类断言**：凡输出中出现此类时间性断言（包括“暂无相关规定”“尚在制定中”“最新一批／最新版本”），必须先带时间限定词联网检索确认，不得凭记忆断言；检索后仍不确定的，改为限定表述并注明检索截止时间。
4. **题面未给定的外部数值**（市场利率、统计标准、缴费基数等随时间变化的数据）：不得编造具体数值。未经检索核实的，用文字表述计算规则（如“按付款日适用的相应利率标准计算”）或留占位符。

## 4. 制作法律版本与法源表

对每条决定结论的规则记录：

| 项目 | 必填内容 |
|---|---|
| 法源 | 法规全称、条号、发布机关、效力层级 |
| 状态 | 现行有效、已修改、失效或尚未生效 |
| 时间 | 发布日、施行日、案件法律事实日期 |
| 地域 | 全国或具体地区 |
| 适用理由 | 为何适用该版本；是否存在特别法、司法解释或过渡条款 |
| 来源 | 元典返回的可跳转 URL |

案件法律事实发生在新法施行前时，不得只因新法当前有效就直接适用。先查时间效力规定；没有溯及依据时，以行为发生时规则为主，并将现行规则作为风险提示而非当然依据。

## 5. 将规则拆成可适用要件

不得把附条件规则压缩成固定比例或绝对结论。每条核心规则至少拆出：

1. 适用主体；
2. 前提事实；
3. 构成要件；
4. 例外、但书和期间限制；
5. 举证责任；
6. 法律后果及上限、下限或裁量空间。

遇到“有过错”“造成损失”“不应超过”“可以”“但书”“除外”等词时，必须逐项分析，不得直接输出唯一比例。司法解释与上位法、实体规则与程序规则应在论证中衔接，不能只在文末罗列。

引用条文的定位精度到“条-款-项”：写明并核对款、项序号，与 `article_detail` 返回原文逐一对应，不得只核对到条。同时确认三件事：该条所处的章节或专节是否限制其适用范围；条文设定的数额档位、主体类型、程序阶段与本案事实是否匹配；转述的法律后果与原文后果同档（不得把仅适用于某一档位或某一程序场景的规则写成一般规则）。同一制度内存在按主体身份、程序角色或阶段区分的相邻或平行条款时（不同条款分别规范不同主体的义务），先逐条比对各候选条款的规范对象，选用与本案主体和争点最直接对应的条文；上位概念条款不得顶替有专门规定的直接条款。起草制度、办法类多条文文书时，交付前将文内“本办法第X条”式交叉引用逐一回查指向是否正确。

## 6. 完成事实涵摄

按以下格式逐项推演：

> 已核实事实 → 对应法律要件 → 证据及证明力 → 对方抗辩 → 暂定结论

将结论区分为：

- 已有证据足以支持；
- 补充某项证据后可支持；
- 存在两种裁判路径；
- 只能作风险判断，不能下确定结论。

权威案例与初步推理冲突时，以核实后的权威规则为准并解释差异。不要为了显得谨慎而制造法条不存在的争议，也不要把真正存在的裁判分歧隐藏掉。

## 7. 独立校验金额和期间

计算前先列参数，不要边写文书边心算：

| 参数 | 内容 |
|---|---|
| 计算项目 | 本金、利息、违约金、经济补偿、赔偿、刑事数额等 |
| 法律性质 | 一般债务利息、加倍部分债务利息、损失赔偿等 |
| 基数 | 纳入项目及法律依据 |
| 排除项 | 诉讼费、一般利息、已返还款等是否排除及依据 |
| 比率 | 日、月、年利率或法定倍数 |
| 起止日 | 起算规则、截止事件、是否含首尾日 |
| 分段事件 | 部分履行、利率变化、新法施行、工资变化等 |
| 结果 | 公式、分步结果、四舍五入规则 |

先验证项目的法律性质，再验证基数、比例和期间。对存在争议的纳入项检索针对性案例。把正确计算路径与常见错误路径分开说明；题面数据不足时提供公式和条件式结果，不伪造精确金额。

**自洽复算（交付前必做）**：文书内出现分项金额与合计数的，交付前脱离原推导过程重新加总一遍，分项之和必须等于合计数；期间类参数（利息期间、期限、年限）按起止日期单独重算，并与正文文字表述（起算日、截止事件）逐一对照。复算不一致时以重算结果为准修正全部关联数字，不得只改合计或只改分项。

## 8. 起草可执行文书

正式起草前确认请求或条款可识别、可证明、可计算、可执行：

- 主体名称、身份、管辖和程序阶段准确；
- 每项请求具有独立请求权基础，并与事实、证据、金额对应；
- 利息写明基数、利率、起止时间和截止事件；
- 通知写明生效方式、到达证据和办理期限；
- 授权事项区分一般授权和特别授权；
- 证据目录对应待证事实，不把法律分析写成证据；
- 未核实内容使用占位符或条件表达，不伪造成既定事实。

结论先行，保留与争点最相关的法条和 1 至 3 个最有力案例，避免法条及案例堆砌。凡元典结果带 URL，在对话回复的引用处附可跳转 Markdown 链接。

### 8.1 文书体例与本体纯净

**体例要素**：按文书类型补全必备要素并保持通行顺序——标题、当事人栏、请求／主文部分、事实与理由、证据说明、致送对象、落款（署名与日期）、附项。**具体文书类型以第 1 步查得的模板参考文件为准**：其体例骨架决定要素顺序，必备要素清单逐项对照补全（含当事人栏细项、落款要素、盖章／签名占位、附项内容），填写要点与常见错误在交付前逐条复查。**题目指令与模板要素是并集关系（硬约束）**：题目显性指令决定正文内容与章节排序，但模板必备要素章节（如声明事项、服务团队、费用安排、结论性表态、落款块、承诺保障等）**即使题目未点名也必须补齐**——题目未提及≠可以省略，仅当模板要素与题目指令直接冲突时才让位于题目。交付前把模板必备要素清单从头到尾过一遍，缺一项即返工。说理性文书（代理意见、辩护意见、意见书类）须有开头导入段（受托来源、程序阶段）与结尾归纳段。论证所需的管辖、时效等程序性内容写在正文对应位置，不得置于落款之后。

**文种优先，禁止万能套版**：按 [法律文书体例与版式决策指南](references/legal-document-style-guide.md) 选择表达形式。传统诉状、答辩状、上诉状等程序性文书采用紧凑当事人栏和编号请求；律师函保持函件体；公司决议保持会议决议体；内部制度保持章条体；只有篇幅和交付场景确有需要的意见书、报告、服务方案才考虑封面或目录。不得把所有文书都改造成“标题＋多张表格＋封面”的报告样式。

**紧凑当事人栏（传统文书硬约束）**：未明确要求官方要素式表单时，一个当事主体使用一个自然段，主体名称或姓名、住所、统一社会信用代码／身份证件信息、联系方式等已知字段以全角逗号连接；法定代表人、主要负责人或委托诉讼代理人可另起一段，但其内部字段仍紧凑排列。允许 Word 在页宽处自然换行，不得在每个字段后手工换行，也不得用大块空白表格容纳少量已知信息。只有法院／机构指定、用户明确要求或用户提供的官方要素式模板才走表格路线。

**结论式说理标题**：诉讼理由、上诉理由、代理意见、辩护意见和法律分析的小标题应直接陈述本节结论，再在正文中按事实、证据、规则和涵摄展开；避免“关于合同责任”“法律分析”“其他问题”等不能传递观点的空泛标题。制度条文、决议和律师函仍按其文种使用简洁功能性标题，不强行写成长句。

**保守使用可见表格**：证据清单原则上必须使用“序号／证据名称／证明目的（或证明事项）”原生表格。其他内容默认保留符合文种习惯的段落、编号条款或简洁列表；只有存在稳定列字段、多条记录确需横向比较／逐列核对／复算，并且改用段落会显著重复标签或增加误读风险时才使用表格。不能仅因内容有两项以上就表格化。传统当事人栏、诉讼／仲裁／答辩／上诉请求、事实与理由、代理和辩护说理、律师函正文、决议正文、制度章条通常不得表格化。复杂金额、密集时间线、权限矩阵、阶段计划可以评估使用表格，但简单数字、少量事件和单一公式用正文即可。

**文字与行距基准**：除指定模板或用户另有要求外，文档唯一大标题使用宋体二号（22 pt）加粗、黑色、居中；全部小标题使用仿宋四号（14 pt）加粗、黑色；正文使用仿宋四号（14 pt）、黑色，默认不加粗，仅对确有辨识价值的短标签、合计或关键结论局部加粗。大标题、小标题、当事人栏、请求、正文、列表、题注、致送对象和落款统一使用 1.5 倍行距（表格单元格用单倍行距保持紧凑，是唯一常设例外）；不得以固定行高或连续空行模拟。封面及页眉页脚可按其功能单独设置。具体 OpenXML 字体、段落和分页实现由 `docx` skill 负责，本 skill 不自行生成 Word 格式。

**落款日期**：材料给定了作成或提交日期的，必须采用给定日期；未给定的，日期栏留白（“年 月 日”式占位），不得填写成稿当日或任何无材料依据的日期。

**正文时间锚点**：正文中“至今”“现已逾期／届满 X 日”等相对时间表述的基准日，以题目给定的时间线为准，不得默认取生成当日；无法从材料确定基准日的，改用“截至［基准日］”占位表述。文书内所有时间表述（节点计划、期间计算、事实叙述）须相互一致，交付前对照一遍。

**本体纯净（硬约束）**：可交付文书文件的本体内不得出现——免责声明、AI 或助手身份说明、“未经核验／未经原文核验／要旨归纳／转引自”等核验状态标注、检索过程说明、数据库来源链接或工具名。这些内容一律移至对话回复：核验状态并入“待确认事项”，链接附在回复的引用处。文书本体中确未核实的引用，删除或改为占位符。

**文书内引号纪律**：文书本体中，引号（“”）只用于与检索原文逐字一致的条文或裁判文书原文（可截取，不得改写）；凡压缩、改写、归纳后的内容一律去引号改为转述句式（如“该院认为……”“该案确立了……的裁判规则”），转述须忠实原意、判项性质不得美化或反转。文书内不使用“要旨归纳”等标注（该标注仅用于对话回复），引号本身就是逐字一致的承诺。交付前逐个引号核对一遍。

**立场文书语气**：代理、答辩、辩护类文书站在委托方立场行文。对己方不利的事实或观点，以“该节应由裁判者依法审查认定”“即便如此亦不影响……”等审查框架或备位框架呈现，不得以第一人称承认句式自认瑕疵或不利结论；题目要求正反分析的，正反内容组织进主位／备位层次或单独的分析段落，而不是在文书中直接让步。请求部分（诉讼请求、答辩请求、仲裁请求）用判项式短句表述可裁判的具体事项，不写成论证句或“依法审查”类程序性表述。

**发表主体一致**：代理词、辩护词、代理意见的发表主体是代理人／辩护人：首部写明受托来源与代理何方，观点句以“代理人认为”“辩护人认为”表述；不得以当事人自称口吻（“本局”“本院”“本公司”“本人认为”）发表代理意见，也不得在同一文书内混用两种发表主体。首部当事人与程序地位表述须与题目给定的诉讼地位一致，主语不得歧义。

**附带分析的交付载体**：题目要求的附带分析、说明或判断（资格判断、策略建议、风险提示等）属于交付物的一部分：与文书本体明确区隔后，写入同一交付文件的附页，或形成独立的附随说明文件（默认同为 docx，输出到 `outputs/`）。仅在对话回复中给出而不落入任何交付文件，视为该项任务未交付。

### 8.2 docx 交付

无特殊说明时，可交付文书以 docx 格式输出到 `outputs/`。凡从头起草并生成 Word 文书，法律内容定稿后必须同时读取并执行 `docx` skill，使用其 **C# + OpenXML SDK Create** 路线生成文件。本 skill 只负责法律研究、内容起草和法律审校，不负责替代 `docx` skill 的排版与文件生成流程。

1. 按本 skill 完成法律检索、文书体例确认、内容定稿和法律审校。
2. 完整读取 `skills/docx/SKILL.md`，按其中的 Create 路线执行；每个从头起草的新法律文书必须使用统一入口执行 `init --fresh`，从该命令返回的已验证法律文书骨架编辑 `Program.cs`，再完成独立 `compile`、`build`、OpenXML 修复与校验。对最终 DOCX 必须继续执行 `render`，再按 docx skill 的视觉自检章节用内置 `image` 工具逐批检查全部渲染页并在交付说明中记录结论，不得因 `build` 或 OpenXML 校验已经通过而省略。
3. 本 skill 不提供或调用任何 Word 排版、生成或格式转换脚本；不得以先写 Markdown 再用本地 Python 脚本转换的方式绕过 `docx` skill。
4. `docx` skill 的生成与校验通过后，再运行 `{python} skills/legal-research-drafting/scripts/check_docx.py <输出.docx>`（`{python}` 是 Python 3 启动器占位符,不可写死 `python3`。取值:macOS/Linux 运行 `python3 --version`,退出码 0 且输出以 `Python 3` 开头即用 `python3`;Windows 先试 平台 PATH 里的 `python`,不可用(退出码 9009,或输出含 `Microsoft Store`/`App Execution Alias`/`应用商店` 假桩文本)再试 `py -3`。逐条命令单独探测,命中即停） 做法律文书本体纯净与格式残留检查；每一项 ERROR 必须修复，WARN 逐项人工判断。
5. 交付前抽读 docx，确认文件可打开、内容完整，并与已经审校的法律文本一致。

**交付门禁（硬约束）**：从头起草的 Word 文书未读取 `docx` skill、未走 C# Create 路线、未完成其 OpenXML 校验、未生成最终版页面渲染、未完成 `image` 工具多模态检查并记录结论，或者未运行本 skill 的 `check_docx.py` 并使 ERROR 清零，均不得列入交付物。各项校验相互补充，不能互相替代。

## 9. 提交前审校

提交前完整读取并执行 [最终审校清单](references/final-review-checklist.md)。发现任一主线法条未取详情、版本未核实、案例未读全文、计算参数缺失、显性指令未销项或请求不可执行时，返回相应步骤修正，不得直接交付。

用户设置字数或案例数量上限时，在输出前做机械检查：案例数量逐项计数；字数按可见正文保守估算并预留余量。超限时先删检索过程、重复引文、扩展背景和次要依据，只保留结论、最直接法条、必要涵摄及免责声明；不得以完整性为由突破硬限制。

法律输出必须附免责声明：本输出为初稿参考，不构成正式法律意见，请执业法律专业人员复核后定稿。免责声明只写在对话回复末尾或交付说明中，不得写入可交付文书文件的本体。
