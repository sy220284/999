# Contract Review Skill

> 本文件只讲怎么审合同。读写文档用当前环境实际可用的文档工具，工具怎么调以工具自身说明为准；本文件不绑定任何具体工具。

## 开始前：确认偏好

先从当前会话提取已明确的审核偏好。缺“修订风格”或“立场强度”时，把缺失问题集中发出并等待回复；已有明确回答不重复问，不生成问询Widget。

一问改法：“您希望我怎么改这份合同？A. 只修改必须修改的条款，批注按可直接交付的表述撰写；B. 从头到尾全面修改，可以修改的条款全部修改。”
二问力度：“条款立场上您希望我怎么把握？A. 最大限度维护我方利益，需要删除或修改的条款直接处理；B. 采取公平适度的立场，兼顾签约可行性，改动较大的方案写在批注里作为建议。”

用户明确回答“随便”“按默认来”时，采用精准修订、强势争取并说明；未回答不是授权默认。用户代表方不能默认。用户选择缓和公平时按其选择执行，不套用默认强势立场。

本期不读写固定MEMORY.md、PROFILE.md或PLAYBOOK.md，不承诺“以后都记住”。偏好只在当前可确认上下文内复用；平台跨Session记忆仅作参考，不代替本次事实和立场确认。用户更改偏好时以当前明确要求为准。

确认立场和核心偏好时，读取[内嵌补充问题](references/intake-questions.md)，按该说明收集特别关注点、标准条款和行业特殊要求；不启动旧cold-start-interview独立流程。

- 精准修订：修改必须修改的条款，可改可不改的不修改，正文改动保持最小；不修改的问题逐条批注，规则见“改法规则”。
- 全面覆盖：从头到尾逐条检查判断是否修改，可以修改的条款全部修改，禁止遗漏可修改的条款；批注标注风险分级，交付时附完整问题清单。
- 强势争取：“立场”小节三项全部执行。
- 缓和公平：执行“立场”小节的“覆盖”“方向”，不执行“力度”。修改以增加对等条款、前提条件、但书、程序为主；只删除违法或显失公平的条款；数值取行业常见值，不取对我方最优值；更激进的方案写入批注。交付前逐条检查改动是否影响对方接受和签约，影响的：正文取双方可接受版本，激进方案写入批注。

## 先确认用户立场

在读取、分析或修改合同正文前，先确认用户代表哪一合同方或交易角色。若用户当前指令和会话上下文没有明确说明，必须停止并向用户追问，等待回复后才能继续；不得先通读合同、调用规则库、检索法律、制作问题清单或开始修改。

不得根据用户持有或上传合同、文件名、起草记录、签署栏、当事人排列顺序或哪一方出现在首页来推断用户立场。不得把用户立场记为「未知」后继续，也不得自行改成中立或双方审查。只有用户明确要求中立审查或同时审查双方立场时，才可采用该范围。

## 通读全文

用户立场确认后，开始任何修改前必须读全文。读完全文才能判断合同类型、确认合同中各当事人的角色与条款关系，并按已确认的用户立场开展审查。读不全就分页续读，直到读完。

双语合同如发现同一条款的两种语言版本，所有修订必须所有语言版本同步修订。双语常见形态：表格双列、段落交替、同段并列、分栏、主文加附录。混合段不能整段替换，定位片段限定到目标语言那一句。

判断合同实质看交易内容，不只看标题。确认合同中各当事人的角色：甲方、乙方或其他交易角色；这一步不得替代前置的用户立场确认。从云端规则库加载该合同类型的审核基线和标准条款：
```bash
{python} skills/contract-review/lib/rules_client.py list-catalog
{python} skills/contract-review/lib/rules_client.py load-by-types '["API/AI采购合同","保密协议"]'
```

以上路径相对含`skills/`的工作区根目录；单独安装时应按实际Skill目录定位脚本。当前环境交付版默认访问对应清言环境地址；不得用`--response-file`的Mock结果代替真实规则查询。

- 必须使用本次`list-catalog`返回的准确类型名称，核对目录`position`与用户交易角色；目录甲方/乙方不必然等于原合同甲方/乙方，按买方/卖方等实质角色确认，不能加载相反立场后声称匹配。
- 客户端统一输出`status/data/warnings/trace_id`。目录在`data.catalog[]`；加载结果在`data`中，优先读取`merged_key_points`和`merged_standard_clauses`，缺失时使用实际返回的`key_points/standard_clauses`。
- `get-baseline <合同类型>`通过单类型load取得基线；`list-types`从目录提取名称；`get-clause <合同类型> <条款名称>`从已加载的合并条款中精确取值。后两者不新建外部接口，get-clause不跨任务缓存。
- 多类型load返回的合并结果以服务端为准。立场冲突、同名条款或父子类型关系无法解释时，标记待确认，不自行假定优先级。
- 无对应类型、空目录、规则库失败时，如实说明规则库检查未完成；可继续基于全文和已核验法律给出审查意见，不能声称已按规则库全量检查。规则库数值和标准条款属于审核基线，不自动等于法定强制要求。

### 必要时核验企业主体

仅在用户要求核验、企业名称存在歧义或主体信息实质影响结论时，由主Agent使用`tianyancha`的企业搜索和基本信息能力；不是每份合同都自动查询。先消歧再详情，标明天眼查及查询日期。查询失败不阻断普通条款审查，只把主体核验标为未完成；不推断无涉诉、无失信或完整尽调已经完成。

- 规则库返回的每个风险标记和 key_point 逐条对照合同处理：已存在且充分 → 不动；已存在不充分 → 修改；缺失 → 补充。行业合规类标记同等处理。
- 规则库未覆盖的合同特有风险、对方单方制裁权、惩罚性条款、跨条款问题，同样逐条处理。
- 双语合同：同一条款的所有语言版本同步修订。混合段禁止整段替换，定位片段限定到目标语言的语句。

## 逐条检查

- 从第 1 条到最后 1 条逐条检查，附件条款与正文条款同等检查。禁止跳过任何条款；禁止以“市场惯例”“行业常见”“无明显问题”为由跳过。
- 每条记录五个判断：我方权利义务；对方权利义务；对我方有利、不利还是中性；履行是否可行，形式对等但履行不可行的同样记录；处理动作，从删、补、改中选定。
- 发现一个问题立即记录四项：条款位置、原文连续片段、问题描述、拟定改法。禁止延后汇总。
- 可疑条款先查证，再决定是否修改。禁止以“不确定”为由跳过。
- 发现没收、不予退还、单方权利、免责、以对方数据为准、视为条款等不利机制 → 全文检查相同机制的条款，同组一并处理。
- 同段或相邻段出现两个不同的数字、期限、名称、比例 → 判定为矛盾。先在全文查第三处线索，包括其他数据、标题、定义、合计计算、“以…为准”条款：能判定 → 改为正确一侧；不能 → 按“矛盾与多解”处理。禁止编造解释调和，禁止搁置不处理。
- 条款含“绝对”“无限”“所有”“任何”“永久”“全部”“无论何种”等无例外词 → 检查故意或重大过失不免责、法定上限不可突破等法定例外，缺失的补上。

### 风险分级

按 严重 → 重大 → 一般 → 次要 的顺序处理。严重和重大未处理完，禁止处理次要问题。五类风险全部检查：法律违规、条款矛盾、保护缺失、立场不利、文字笔误。

| 级别 | 情形 | 处理 |
|---|---|---|
| **严重** | 无上限赔偿或损失，如“承担一切法律责任”“赔偿全部损失”；绝对保证，如“保证不侵权”“保证产品不含任何缺陷”；知识产权全部归对方、己方无例外或保留；单方可无条件终止并扣款、抵销、没收 | 必须改正文，禁止只加批注：加上限、补例外、限缩范围、改成双方对等 |
| **重大** | 保护机制缺失或无效：无验收期限和视为验收条款；无责任总额上限，或上限未排除法定不得免除项；附件写“以本附件为准”但附件不利条款未改；付款不挂钩交付或验收；审计权、检查权无范围限制 | 必须补或修：补条款、限缩范围、同步修改附件 |
| **一般** | 违约金过高、整改期过短、单方裁量权、以对方数据为准、管辖在对方所在地 | 逐条修改 |
| **次要** | 错字、标点、编号、交叉引用 | 最后批量处理 |

### 附件专审

全文读完后执行第二轮：

- 逐条核对正文对附件的引用：编号、名称、内容与附件实际是否一致。
- 附件中的数字、期限、主体，逐项与正文同一事项比对。
- 清点附件：清单所列份数、实际份数、名称逐项核对。
- 附件条款按正文同等标准逐条检查、修改。

### 争议解决条款

每份合同单独检查：仲裁机构是否明确、管辖地在我方还是对方所在地、适用法律是否对我方有利。空白或约定不明的，改为可执行方案。涉外合同必须检查适用法律和管辖。

### 全文检查项

| 检查项 | 内容 |
|------|----------|
| 文字一致性 | 主体名称、金额大小写、日期、编号前后一致 |
| 时间线 | 签约、交付、验收、付款、到期各节点衔接，日期先后不颠倒。涉及合同期限、到期日、有效期时，用 `{python} -c "from datetime import date; print(date.today())"` 取当天日期，结合签订日、服务期、质保期、交付周期推算正确期限 |
| 金额核算 | 总额=分项之和；含税、不含税、税率对应；付款节点覆盖100%；价格表逐行重算 |
| 权利义务对等 | 分别列出我方义务和对方义务，核对数量和严重程度是否对等 |
| 最大风险 | 标记出我方最大风险条款 |
| 修改可执行性 | 修改后的条款在履行中可执行、不产生争议 |

## 数值核验

查证顺序：

- 法定数值先用 `legal-statute-retrieval` 查现行标准。数据库未命中或涉及最新修正，再用 `legal-web-search` 检索、`web-page-fetch` 取官方原文核对。
- 每个法定值以本次查证结果为准，每次都实际查证。禁止凭记忆写入，禁止照抄本 skill 中的数值。

核验范围：

- 税率、比例、期限、金额上限等具体数值逐项核验，禁止因数值看起来合理而跳过。形似占位符的数值同样核验。
- 税率税种、法定比例上限、法定期间、利率等法定强制值，按交易实质核验合法性。
- 诉讼时效等法定期间的变更约定多数无效。必须删除违法约定、恢复法定状态。禁止只把数字改成法定值。

计算：

- 价格表、付款比例、数量加总、税额、金额大小写、日期先后顺序，必须用代码实际计算。
- 价格表逐行验算不含税价 × 税率 = 税额，验算各行小计与合计一致。禁止只验算总额。
- 金额大写与小写逐项核对一致。
- 计算发现不一致的，把算式写入批注。

## 法律核验

- 合同引用的法律名称、条文序号、陈述的法律规则，必须用 `legal-statute-retrieval` 取现行原文逐项核对法律名称、条号内容、规则表述。数据库拿不准或涉及最新修正，用 `legal-web-search` 加 `web-page-fetch` 核对官方原文。
- 引用与现行法不符的，改为正确引用并在批注说明。
- 法律风险、权利义务失衡、合规类批注，必须写明具体法律名称和条款号。写不出条号的，先查 `legal-statute-retrieval` 再写。禁止只写行业惯例或利益平衡而不引法条。纯文字笔误、格式统一类批注无需法条依据。
- 批注只写法律法规名称和条文号，禁止写规则库内部编号。
- 新增条款引用其他条款号前，在全文搜索确认该条款号存在。不能确认的禁止引用。

## 行业法规检索

- 确认合同类型后，用 `legal-statute-retrieval` 查法条原文、`legal-web-search` 查最新修订和实施情况。两个工具并行调用，不等一个失败再调另一个。
- 检索维度：交易标的、当事人业务性质、数据处理方式、技术特征。禁止只检索民法典通用条文。
- 查到强制性要求的，列出该法规要求的合规条款清单，逐条对照合同：缺失的新增，不符合的按法规修改。新增条款写明法规依据。

## 改法规则

- 定性决定动作，禁止降级：定性为删 → 整条删除；定性为补 → 新增条款；定性为补的禁止只写批注建议。该删的禁止用调数字代替整条重写。
- 删：整条删除该条款。
- 补：新增条款，作为独立新段落。
- 改：错字、标点、编号只改必须改的字；条款方向错误或权利义务失衡的，重写整条为完整自洽条文。
- 修订范围只选真正变化的字，禁止选整句整短语。
- 必须修改的问题同时有正文修订和批注：正文为修改后的完整条款，批注说明修改理由。纯错字、标点可只改不批注。精准修订下不修改的问题，逐条批注写明风险和建议改法。
- 批注文风：精准修订下，批注禁止使用“严重”“重大”等分级前缀和内部评估用语，写成可直接交付的专业修改理由；全面覆盖下，批注必须标注风险分级，分级为严重、重大、一般、次要。
- 精准修订下：支付比例、价格、付款节奏等商务条款不直接修改正文，以批注写明问题、风险和建议方案，建议数值用【】标注，由用户决策；我方立场或双方地位无法确定的问题，以批注提示；对方明显强势、直接修改影响签约的条款，正文保持原文，更激进的方案写进批注。用户明确要求修改的除外。
- 矛盾类批注必须写明：互相矛盾的两条、各自原文、判定依据、修改后为何自洽。
- 修改一条中的某句后，检查同条其他句子是否仍成立；付款条件与开票条件、义务与违约金、权利与行使条件必须同步修改。
- 修改后措辞禁止有歧义。新增条款禁止与已有条款内容重合。引用其他条款号前核对存在且正确。

“立场”小节三项的执行范围：强势争取全部执行；缓和公平执行覆盖、方向，不执行力度：

- 覆盖：第一轮记录完成后，全文再检查一遍，逐条判定有利、不利、中性；不利条款全部处理，禁止以市场惯例或程度轻微为由跳过。
- 力度：责任上限、违约金、补救期限、单方权利的数值必须实际起到限制风险的作用。禁止保留无上限责任条款；禁止把上限改得比原合同更宽松。
- 方向：每次修改前判断该修改对我方有利还是有害。对我方有利的条款保留原状，禁止缩短、删除、改成对等。修改后复查方向未反向。全文立场一致，关联条款同步处理。

矛盾与多解，无第三处线索可判定时：

- 影响商业实质或当事人真实意图的 → 按既定立场选对我方最有利的一侧修改，批注写明各可选方向、依据缺失、建议用户或律师复核确认。
- 多个终态都合法完整、仅偏好不同的 → 按既定立场选对我方最有利的一侧修改，批注注明另一方向同样成立。
- 只有约束、无唯一值的 → 任选一个满足约束的合理值，用【】标注，批注写明所依据的约束和假设。

## 修改后核验

每批修改落盘后重新读一遍文档核对（优先一次取全文；文档过长再按页段取），不依赖额外核验工具：
- 新文本已逐字落盘：新增/改写后的关键句在文档里逐字找得到。
- 被替换的原文已不存在：旧表述在全文无残留。
- 修订与批注数量、位置与问题清单一一对应。
- 逐条对照问题清单，每个问题都有对应改动；遗漏的补改后重新读文档核对。

## 交付文件命名

交付文件名必须带版本号：同一份合同第一轮修改交付命名为 `<合同>_第一版.docx`，之后每完成新一轮修改依次递增为 `_第二版.docx`、`_第三版.docx`。交付前先查已交付到第几版，新版本号接着往下编。同一轮里的修补重试不算新一轮修改，版本号不变。用户明确指定文件名时按用户指定的命名。

## 交付前自检

逐项执行：
- 逐条对照批注列表，每条批注对应的段落必须有正文修订。只有批注没有修订的，补上修订。
- 改过的条款，检查同条其他句子是否还自洽。
- 新增条款引用的条款号，在全文搜索确认存在。
- 附件里的不利条款有没有改。不能只改正文不改附件。
- 严重风险和重大风险是否全部落地。不只是批注了，是正文也改了。
- 交付文件名版本号与修改轮次一致，符合「交付文件命名」规则。
