# V8 与搜索依赖接入记录

本次只提交源码与静态检查结果。没有执行构建入口，没有提供 V8、rg 或引擎二进制。

## 搜索程序

上传原版 `scripts/codex_package/rg` 锁定 ripgrep 15.2.0。Android 构建入口 `构建安卓搜索.sh` 固定该 tag 对应提交 `e89fff89ac9af12e8d4ce9d5fd07beb408ca730f`，使用锁文件、Rust 1.99.1、NDK 28.2.13676358、API 35 Bionic 和 16 KB 链接对齐，为 arm64-v8a / x86_64 生成 `libcodex_rg.so`。入口保留三个原始许可证到应用资源。

依赖适配补丁让 Android 的 InstallContext 从当前引擎所在安装目录查找 `libcodex_rg.so`，避免错误使用桌面 Linux 包。缺文件时让调用失败，不下载或生成替身。

当前入口启用 `--features pcre2` 和上游支持的 `PCRE2_SYS_STATIC=1`，跳过构建机 pkg-config 的系统 PCRE2，使用锁文件中的 pcre2 0.2.11 / pcre2-sys 0.2.10 及其内置 PCRE2 10.46。对应 crate 校验和见核心宿主清单；pcre2-sys 源 tag 对应提交 `fd05026e1bf3ad62b3876cf9bd952dc742368462`。上游 build.rs 对 aarch64-linux-android 禁用 JIT，保留解释执行；本项目没有用关闭 PCRE2 或空库替代。

构建后使用同一 features 的 Cargo metadata 定位实际依赖，保留 pcre2/pcre2-sys 的原始许可证及内置 PCRE2/SLJIT 的源文件版权/许可声明。脚本、许可证整理和新增 1 项 Android Rust 安装路径测试均未运行。

路径审阅：原版 thread-store 与 CLI doctor 通过 InstallContext 查找，已适配安装目录；file-search 使用自身 Rust 实现。模型在通用 shell 中直接输入 `rg` 的命令名称映射已增加安装目录符号链接与 PATH 代码，但仍未做 Android 执行验证，不能因 thread-store 路径已补就称全部搜索工具可用。手机真实执行、大目录性能、取消、链接及 16 KB 页仍待后续验证。构建脚本存在不代表已跨编译通过。

## V8 供应约束

原版依赖为 Rusty V8 152.2.0，源提交 `2768994f664e8a6e3aba27503606c58339136e2a`；Cargo.lock 中 crate SHA-256 为 `a10fe1a92da5c32c7c7f838ce36c0ccfcfd5edf0865b58bdde820aa64cea9888`。上游 build.rs 的 Android 源构建包含自动获取 NDK r26c 和部分分支依赖，当前没有将这些下载链改造成完整可复现供应链。因此未声称已完成 V8 的 Android 源构建。

核心入口要求 `CODEX_ANDROID_V8_MANIFEST` 指向供应方提供的真实 JSON 清单。`核对V8供应.py` 在任何 Cargo 调用之前检查版本、提交、target、NDK、features、GN 声明、归档与同批生成绑定各自的 SHA-256，以及归档 ELF 架构。只接受完整未压缩非 thin `.a`；不接受 Linux `.so` 或空文件。随后复制到构建目录并设置上游支持的 `RUSTY_V8_ARCHIVE`、`RUSTY_V8_ARCHIVE_SHA256`、`RUSTY_V8_SRC_BINDING_PATH`，关闭源构建/跳过下载/文档模式等绕过路径。

供应清单需要以下字段；没有默认哈希或示例占位产物：

| 字段 | 必须值/说明 |
| --- | --- |
| version | `152.2.0` |
| source_commit | 上述 Rusty V8 固定提交 |
| target | `aarch64-linux-android` 或 `x86_64-linux-android`，匹配当前构建 |
| ndk | `28.2.13676358` |
| profile | `release`（上游默认预构建 V8 模式，与 Cargo dev-small 无关） |
| features | `use_custom_libcxx`、`v8_enable_pointer_compression`、`v8_enable_sandbox` 三项 |
| gn_args | 对象；至少包括 target_os=`android`、target_cpu=`arm64`/`x64`、use_custom_libcxx=true、v8_enable_pointer_compression=true、v8_enable_sandbox=true、is_debug=false |
| build_provenance | 非空的构建来源/任务/完整依赖锁定记录 |
| archive | 对象：path 为相对清单目录或绝对的 `.a` 文件路径，sha256 为其真实小写 64 位哈希 |
| bindings | 对象：path 为同批生成的 Rust bindings，sha256 为其真实小写 64 位哈希 |

清单内容属于供应方声明。静态核对只能拒绝明显版本、完整性和架构错误，不能凭 ELF 区分同架构 Linux 与 Bionic，也不能证明绑定 ABI、GN 实际生效、V8 sandbox 或 Android 17 运行正确。下一步必须取得可追溯的真实 Android 构建，再做链接与设备验收。

来源：上传原版 Cargo.toml/Cargo.lock、scripts/codex_package/rg；[ripgrep 固定提交](https://github.com/BurntSushi/ripgrep/tree/e89fff89ac9af12e8d4ce9d5fd07beb408ca730f)、[Rusty V8 固定提交](https://github.com/denoland/rusty_v8/tree/2768994f664e8a6e3aba27503606c58339136e2a)。

PCRE2 构建来源：[pcre2-sys 固定 build.rs](https://github.com/BurntSushi/rust-pcre2/blob/fd05026e1bf3ad62b3876cf9bd952dc742368462/pcre2-sys/build.rs)。

## 2026-10-27 P1 静态审阅后的工具闭环补充（尚未执行）

- `构建安卓核心.sh` 默认的 `source` 路径按 ABI 隔离 `original-engine-source-arm64-v8a` / `original-engine-source-x86_64`，同一 ABI 的 engine 与 code-mode 继续共享固定 Rust 源码和目标目录。通过 `CODEX_ANDROID_BUILD_DIR` 自定义路径时由操作者保证 ABI 隔离。
- `准备V8源码.py` 对 Linux x86_64 宿主和固定 Rusty V8 152.2.0 提前核对；上游 `tools/ninja_gn_binaries.py` 使用 DEPS 版本标签从 CIPD 下载工具，仅凭标签无法独立证明得到的 GN/Ninja 二进制没有变化。为避免“下载成功即信任”，现在要求外部核实的 `CODEX_ANDROID_V8_TOOL_LOCK` JSON，并在执行构建前逐字节计算 GN/Ninja SHA-256，不匹配就停止。
- 工具锁必须包含 `source_commit`（`2768994f664e8a6e3aba27503606c58339136e2a`）、`host`（`linux-x86_64`）、`gn_version`（`641ace93dd9560e75e7add0d08f77b446fbb3b78`）、`ninja_version`（`1.12.1.chromium.4`）及经独立核验的 `gn_sha256`、`ninja_sha256`（小写64位十六进制）。脚本不自动生成、信任或补写这些校验值，避免首次运行时自我背书。
- `source-provenance.json` 同时记录工具校验结果及工具锁文件哈希，用于后续核查实际来源；`supply` 模式继续坚持原有归档/绑定双文件 SHA 校验。两种路径均未运行，本轮没有产生锁文件、V8 归档、Rust 绑定或 ELF。须由实际构建环境先取得可信工具哈希、核实 DEPS 其他获取链与 GN/NDK 参数，再开展源构建、链接及设备验证。当前仍不能称为可复现构建已验证。
- 通用原版工具路径方面，`AndroidToolPaths` 已在安装目录有真实 ELF 时创建 `rg` / `git` 命令别名供继承的 PATH 查找；缺 ELF 只报告缺失，不将安装路径代码视为工具启动通过。

对应原版固定入口：`codex-rs/install-context/src/lib.rs` → `libcodex_rg.so` / `libcodex_code_mode_host.so`；`code-mode/src/remote_session` 经独立长度帧与 Hello 握手启动宿主；`app-server`、`arg0` 的 helper/补丁工具复用 `libcodex_engine.so` 分发。Android UID 仍无原版桌面项目沙箱保证。
